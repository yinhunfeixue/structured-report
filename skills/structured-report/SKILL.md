# 结构化汇报写作

## 触发约束

本 skill 只在用户显式调用时生效。若当前请求不含上述显式指令，忽略本文件全部内容，按常规方式回应。

## 输出边界（优先于后面所有步骤）

不设字数上限。约束的是内容：写什么、写几条、每条携带多少信息。

### 写什么

**1. 范围锁定**

只写用户点名要的内容。用户说「写 9 月工作汇报」，就只写 9 月做了什么。

未经要求不得添加：下期计划、上期承诺回顾、风险清单、人员与资源、组织架构、方法论说明、附录。

模板是菜单不是清单：`assets/` 里的章节按需取用，用不到的整节删掉，不留空壳、不用「无」或「待补」占位。

缺了用户会问，多了用户得自己删。

**2. 归属与出处**

三类内容必须标注，否则是虚报：

| 情况 | 写法 |
|---|---|
| 成果里含他人产出 | 注明产出者与分工边界 |
| 数据转自他人材料、日志、提交记录 | 注明出处，如「据 {来源}」 |
| 结论未经二次验证 | 前缀「判断：」或「推测：」 |

指标比正文更容易失信。一个「从 X 增长到 Y」的指标，若增量里含他人产出，必须在表下注明分工，否则整张指标表连带失信。

### 怎么写

**3. 结构配额**

| 层级 | 配额 | 超了怎么办 |
|---|---|---|
| 结论 | 1 句 | 拆不掉说明没想清 |
| 支撑 / 章节 | 3 条，最多 5 | 上抽一层重新归类 |
| 每节的列表项 | 3 条，最多 5 | 留 Top 3，其余合并成一句总计 |
| 每个列表项 | 1~2 句 | 拆成两项，或把第二句降级删掉 |
| 嵌套深度 | 节 → 列表项，2 层 | 第三层的内容并进父项 |

**4. 信息密度**

每个列表项必须携带一个新事实，属于下面四类之一：

| 类型 | 形态 |
|---|---|
| 数据 | 某个量从 X 变成 Y，或达到 X（配基准） |
| 根因 | 现象由某个具体机制引起 |
| 状态变化 | 某项能力从不可用变可用，或边界发生移动 |
| 口径定义 | 某个指标的统计范围是什么 |

四类都不属于的项直接删。判据：去掉这项，读者会不会少知道一件事。

只描述动作与感受的项一律删 —— 「完成了重构，结构更清晰」「修复了若干问题」「推动了对齐」，三句都答不出「所以呢」。

同一事实只出现一次。在结论里说过的，正文不再复述。

**5. 内容形态**

正文优先列表，不用段落堆叠。每项 = 粗体短语 + 破折号 + 句子，两者同一行：

```
- **{4~8 字短语}** —— {一句话，含数据或根因}。
```

| 错误形态 | 问题 |
|---|---|
| 只有短语的列表项 | 扫得快但读不懂，对方还得来问 |
| 只有句子的列表项 | 要读完才知道这条讲什么 |
| 短语当 `###` 标题，下面跟段落 | 短语占了标题层，目录读不出结论 |

标题层留给结论句（见 `references/principles.md` 第 14 条），短语下沉到列表项。

段落只在两种情况用：单句结论，或「判断：」开头的归因。

表格规则见 `references/writing-rules.md` 规则 11。

## 第一步：固化口径（素材未确认时不要开写）

汇报错在口径上，整篇作废；错在文字上，改几句就好。所以先做这步。

动手前把下面这张表填满，填不出的问用户：

| 项 | 要确认什么 | 常见坑 |
|---|---|---|
| 数据源 | 从哪个库 / 仓库 / 文档取，命令或路径写下来 | 只看单一来源，漏掉另一半素材 |
| 时间边界 | 起止日期，含不含边界当天 | 「9 月」是哪一年；素材实际只到 9/18 却报成整月 |
| 主体标识 | 人名 / 账号 / 团队的全部别名 | 同一人有多个用户名或显示名，按一个查会漏 |
| 纳入排除 | 哪些算、哪些不算 | 合并提交、自动化产出、他人代提交 |
| 基准来源 | 上期 / 目标 / 同比的数取自哪 | 有数据无基准，等于没有信息 |

口径要写进文档头部，让读者能复现。实际范围与用户说法不一致时，按实际写并在头部说明。

## 第二步：锁定五要素

| 要素 | 说明 | 缺失时 |
|---|---|---|
| 受众 | 老板 / 平级 / 下级 / 客户。决定详略与用词 | 必问 |
| 决策点 | 需要对方做什么决定、给什么资源 | 先按「无需决策」写，成稿后追问一句 |
| 目的 | 让对方知道、认同、还是拍板 | 由受众与决策点推定 |
| 篇幅 | 走结构配额，不按字数 | 用默认配额 |
| 口径 | 见第一步 | 必问 |

只有受众和口径值得停下来问。其余取默认值继续写，成稿后一次性确认，不要为每一项各问一轮。

## 第三步：结论先行

开头就是结论，不是背景。固定形态：

```
【结论】一句话，≤40 字，含判断和动作。
【支撑】3 条列表项，每条 = **粗体短语** —— 一句话展开。
【待决】需要对方拍板的事项，没有就写"无需决策"。
```

禁止开篇写「本周我们做了以下工作」「首先介绍一下背景」。

## 第四步：搭骨架

选一个框架，不混用。详见 `references/frameworks.md`。

- 汇报进展 → 金字塔（论·证·类·比）
- 提出问题求资源 → SCQA（情境·冲突·疑问·回答）
- 讲个人/团队成绩 → STAR（情境·任务·行动·结果）
- 做方案对比 → 维度矩阵

同层级条目必须 MECE（不重不漏），且句式平行：要么全是动宾短语，要么全是名词短语。

## 第五步：填证据

- 每个判断后面跟数据，数据后面跟基准（环比 / 同比 / 目标 / 行业值）
- 事实、观点、转述三分：观点前加「判断：」，转述数据注明出处
- 形容词换成数字：删掉「大幅」「明显」「有效」「显著」

## 第六步：精简

执行 `references/writing-rules.md` 的改写规则。验收标准是内容判据，不是字数：

- 每个列表项都携带一个新事实
- 每个层级都在结构配额内
- 同一事实没有出现第二次
- 全文没有超范围的节

删的优先顺序：
1. 超范围的整节
2. 同一事实的第二次表述
3. 铺垫句、过渡句、自我评价
4. 修饰副词
5. 明细条目 —— 留 Top 3，其余合并成一句总计

自检两问：
- So What 测试：每句话问「所以呢」，答不出就删。
- Why 测试：每个结论问「凭什么」，答不出就补证据或降级为假设。

## 第七步：交付前自检

过 `references/checklist.md` 的**硬门禁**六条，全部通过才能交。优化项尽量过，未过的在文末标为已知缺口。

## 改写既有草稿

用户给的是草稿时，跳过第一步到第四步，改走诊断流程：

1. **查结论** —— 第一句是不是结论。不是就从正文里找出来提到开头。
2. **查范围** —— 有没有用户没要的节。有就删，不要保留改进版。
3. **查形态** —— 段落堆叠改列表项，短语标题降级成列表项。
4. **查密度** —— 逐项做信息密度测试，删掉只有形容和过程的项。
5. **查归属** —— 他人产出、转述数据、未验证结论是否标注。

输出「改写后全文」+「关键改动 3 条」，不逐句点评。原文的事实一条都不能丢，只重组和删冗余。

## 本 skill 自身的两条维护约定

- **单一来源** —— 所有硬约束（配额数值、必备章节、门禁条目）只在本文件声明。`references/` 只做展开，不重复声明数值。两处冲突时以本文件为准。
- **不写业务场景** —— 规则与示范一律用占位符和抽象类型，不写行业、产品、模块、真实指标名。示范语言规则时可用通用数值（如「P95 从 1.8s 降到 0.9s」），但不得引入具体业务背景。绑定了业务的规则无法迁移到别的场景，也会把使用者的内部信息留在 skill 里。

## 输出约定

- 直接给成稿，不解释写作过程
- 数据缺口用 `【待补：xxx】` 占位，不编造数字。但不为「用户没要求的章节」建占位行
- 不统计字数、不标字数。篇幅由结构配额与信息密度决定
- 想加用户没要求的内容时，不要直接写进文档。成稿后单独问一句「要不要补 X」
